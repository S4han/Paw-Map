### 1.3 반려동물 동반 조건 필드(`detailPetTour2`)

| 필드 | 의미(보고된 값 예시) | PetPlace 매핑안 | 신뢰도 |
|---|---|---|---|
| `acmpyTypeCd` | 동반 유형 — "전구역 동반가능", "일부구역 동반가능" | `petStatus`·`indoorAllowed` 판단 근거 | ⚠️ |
| `acmpyPsblCpam` | 동반 가능 동물 — "5kg 이하 동반 가능(이동장 이용 필수)" | 크기별 허용(`small/medium/largeDogsAllowed`) | ⚠️ |
| `acmpyNeedMtr` | 동반 시 필요사항 — "목줄 착용, 반려동물 유모차 탑승, 이동장(켄넬)사용" | `leashRequired`, `carrierRequired` | ⚠️ |
| `relaAcdntRiskMtr` 등 `rela*` 계열 | 관련 사고 대비 사항 등. 샘플 110건 중 51건이 `acmpyPsblCpam`과 같은 원문이었다는 보고 | `notes`(원문 보관만) | ⚠️ |
| 그 외(총 약 9개 필드) | 미확인 | — | ❓ |

**설계 영향**
1. 보고된 모든 조건 필드가 **자유 텍스트**다 ⚠️ → 구조화 필드(`smallDogsAllowed` 등)는 **명확한 패턴만** 규칙 파싱하고, 나머지는 원문을 `notes`로 그대로 보여준다(요구사항 FR-009와 일치).
2. 동반 정보가 없는 콘텐츠는 `items`가 객체가 아닌 **빈 문자열 `""`** 로 온다 ⚠️ → 파서가 문자열/객체/배열을 모두 처리해야 한다(공공데이터 API 공통 함정).
3. "일부구역 동반가능"은 `ALLOWED`로 볼지 논의 필요 → **제안: `ALLOWED` + 조건 요약에 "일부 구역만" 표시.** "전구역"과 구분해 보여준다.
4. 전용 서비스 목록에 실려 있다는 사실 자체가 동반 가능 근거인지(목록 = 동반 가능 장소 모음인지) ⚠️ → 2차에서 목록 항목 중 `detailPetTour2`가 "동반 불가"를 주는 사례가 있는지 확인. 확인 전에는 **상세 근거가 있을 때만 `ALLOWED`**.

**파싱 규칙 후보(STEP 7에서 확정, 표본 확대 후)**
- `(\d+(\.\d+)?)\s*kg\s*이하` (대소문자 무시) → `maxWeightKg`, `미만` → `maxWeightKg` + `maxWeightExclusive`
- "전 견종 동반 가능" → **몸무게 제한 없음이 명시된 것**으로 보고 몸무게 조건 충족 처리(값 없음과 구분) — 사용자 승인 필요
- `(\d+)\s*마리까지` (주로 `etcAcmpyInfo`) → `maxDogs`
- "훈련된", "맹견 입마개" 등 수식어는 `notes`로 보존(판정에 쓰지 않음)
- `acmpyTypeCd = 전구역 동반가능` → `indoorAllowed = true`로 볼지 **사용자 승인 필요**(실내 공간이 있는 업소에 한해). `일부구역` → `indoorAllowed` 값 없음

**설계 결정(제안)**
1. `locationBasedList2`는 쓰지 않는다. **시도 단위 `areaBasedList2(lDongRegnCd)` 목록을 받아 서버에서 거리 계산**한다(제주 전체 330건 = 4회 호출). 목록은 단기 캐시해 일 한도를 지킨다(캐시 허용 범위는 V-7).

**설계 영향**
1. **좌표가 없다** → 모든 주소를 지오코딩해야 지도·반경 검색이 가능. 2,813건은 카카오 로컬 주소 검색 일 무료량(보고된 10만 건) 안이지만, 주소 정제(괄호·층 정보 제거) 후 변환 성공률을 STEP 3에서 측정해야 함.
2. **고유 식별자가 없다** (`연번`은 파일 내 순번) → 갱신 시 같은 업소를 추적하려면 `정규화 업소명 + 정규화 주소`로 자체 키를 만들어야 함. 이름·주소가 바뀌면 다른 업소로 보일 수 있음.
3. **날짜가 없다** → `Evidence.checkedAt`을 채울 수 없음. 화면에는 "식약처 목록 등재(목록 조회일 YYYY-MM-DD)"로 표시하고 `lastVerifiedAt`에는 넣지 않는다(요구사항 §7.2).
4. **동반 조건이 없다** → 이 출처만 있는 장소는 프로필 매칭 시 몸무게·실내·2마리 이상 조건이 모두 `NEEDS_CONFIRMATION`. 1마리 + 조건 미입력이면 Q-2에 따라 판정 가능.
5. **카페 판별**: 업종이 일반음식점/휴게음식점/제과점 3종뿐. 휴게음식점 = 카페 후보이나 분식·패스트푸드 등도 포함될 수 있음 → MVP 규칙안: `휴게음식점`·`제과점영업` → `CAFE`, `일반음식점` → `RESTAURANT`, 업소명에 "카페/커피/coffee"가 있으면 `CAFE` 보정. 오분류 가능성을 문서화하고 STEP 6에서 표본 점검.

### 1A.2 판정 규칙에 주는 영향 (중요)

1. **등재 = 영업자가 지자체에 자율 등록 신청한 업소.** 페이지 안내에 따르면 **목록에 없어도** 시설기준·준수사항을 지키면 동반 출입이 가능할 수 있다 🔷.
   → 목록에 **없다는 사실을 `NOT_ALLOWED` 근거로 쓰지 않는다.** 미등재 = 이 출처에서 근거 없음.
2. 등재 업소는 `PetStatus` 근거 `OFFICIAL`(동반 가능)로 쓴다. `checkedAt`은 파일에 등록일 등 날짜 열이 있을 때만 채운다.
3. 제도가 영업장(매장 안) 출입을 다루므로 실내 동반 허용과 관련이 깊지만, 자료에 실내/실외 구분이 있는지 확인 전에는 **`indoorAllowed`를 채우지 않는다**(요구사항 원칙 5: 목록 등재가 실내 입장을 보장하지 않음). 파일 열과 제도 문서를 보고 STEP 3에서 다시 결정.
4. 휴게음식점(카페 포함)·제과점이 대상이라 **음식점·카페 두 카테고리의 공식 근거 후보**가 된다. 카페 판별은 업종명만으로는 부족할 수 있음(휴게음식점에 분식 등도 포함) ❓.
5. 크기·마릿수 조건은 이 자료에 없을 가능성이 높음 ❓ → 프로필 매칭에서는 대부분 `NEEDS_CONFIRMATION`.

### 4.2 결정·제안

1. **동반 정보의 주 출처는 관광공사 + 식약처(공식 근거)** 로 한다. 식약처 미등재는 동반 불가 근거가 아니다(§1A.2).
2. **D-4 Google 활용 범위 → 시나리오 D 제안**: 동반 정보·목록에는 Google을 쓰지 않는다(`allowsDogs` 채움 15%, 최고 등급 과금). Text Search IDs Only(무료)로 "Google 지도에서 보기" 링크만 제공하는 방안은 매칭 정확도 확인 후(STEP 6) 결정.
3. **위치 검색은 시도 단위 목록 + 서버 거리 계산**(`locationBasedList2` 사용 안 함, §1.3-1).
4. **숙소 출처 공백**: 관광공사 숙박은 전국 98건, Google `allowsDogs`는 채움률이 낮다. STEP 3에서 대안을 비교한다 — (a) MVP 숙소는 관광공사 데이터만 표시하고 범위가 좁음을 명시 (b) 숙소 카테고리만 Google 상세 보강(비용 상한 내) (c) 지자체·지역 관광 데이터 등 추가 출처 조사 (d) P1 사용자 제보로 보완.
3. **지역 검색은 카카오 로컬 API, 지도는 Google Maps JS(NearMe 재사용) 유지**를 1안으로 제안. 카카오맵으로 지도까지 통일하는 2안은 무료 쿼터 조건 확인 후 비교.
4. 모든 유료 가능 API는 **콘솔에서 일일 쿼터 상한**을 걸어 무료량을 넘지 못하게 한다(NFR-01).
